# Python Engineering Skill

## 1. Назначение

Определяет инженерные стандарты разработки на Python.

Основные принципы:

- Сначала изучить существующую архитектуру.
- Писать минимальный, понятный и типизированный код.
- Разделять бизнес-логику, инфраструктуру и интерфейсы.
- Использовать TDD.
- Не создавать дублирующие механизмы.
- Проверять фактическую работоспособность изменений.

## 2. Обследование проекта

Перед работой:

1. Прочитать применимые `AGENTS.md`.
2. Изучить `pyproject.toml`, lock-файл и используемый package manager.
3. Определить версию Python.
4. Изучить структуру затрагиваемого модуля.
5. Найти существующие аналоги функциональности.
6. Определить используемые библиотеки и фреймворки.
7. Изучить существующую систему конфигурации, логирования, ошибок и тестирования.
8. Проверить состояние Git.

Не предполагай, что проект использует FastAPI, Django, Flask, SQLAlchemy или Pydantic, пока это не подтверждено.

## 3. Структура проекта

Если существующая архитектура отсутствует, для нового проекта можно использовать:

```text
src/
├── app/
│   ├── main.py
│   ├── config.py
│   └── lifespan.py
│
├── modules/
│   └── users/
│       ├── api/
│       ├── models/
│       ├── schemas/
│       ├── services/
│       ├── repositories/
│       ├── exceptions.py
│       └── tests/
│
├── shared/
│   ├── database/
│   ├── logging/
│   ├── security/
│   └── utils/
│
└── tests/
```

Структура является примером, а не требованием переносить существующие файлы.

### Назначение каталогов

- `api/` — HTTP endpoints, маршруты и контроллеры.
- `models/` — модели хранения данных.
- `schemas/` — структуры входных и выходных данных.
- `services/` — бизнес-логика и сценарии использования.
- `repositories/` — доступ к хранилищам и абстракции получения данных.
- `shared/` — действительно общие механизмы.
- `tests/` — автоматизированные проверки.

Не создавай все каталоги заранее. Добавляй их только при появлении соответствующей ответственности.

## 4. Именование

| Элемент | Правило | Пример |
|---|---|---|
| Файлы | snake_case | `user_service.py` |
| Модули | snake_case | `auth_repository.py` |
| Классы | PascalCase | `UserService` |
| Функции | snake_case | `create_user()` |
| Переменные | snake_case | `user_id` |
| Константы | UPPER_SNAKE_CASE | `MAX_RETRIES` |
| Исключения | PascalCase + Error | `UserNotFoundError` |
| Тесты | test_ prefix | `test_user_service.py` |

Имена должны отражать назначение, а не техническую случайность.

Не используй `helpers.py`, `common.py`, `misc.py` для несвязанных функций.

## 5. Архитектура

Разделяй ответственность:

- API отвечает за взаимодействие с внешним клиентом.
- Schema отвечает за контракт данных.
- Service отвечает за бизнес-сценарий.
- Repository отвечает за доступ к данным.
- Model отражает структуру хранения.

Не превращай Service в универсальный контейнер всех функций.

Не помещай бизнес-логику в HTTP endpoints.

Не создавай Repository, если проект использует другой обоснованный подход к доступу к данным.

Избегай циклических импортов и скрытых зависимостей.

## 6. Python и типизация

- Используй type hints для публичных функций и методов.
- Не используй `Any` без обоснования.
- Предпочитай `Protocol` для структурных интерфейсов, когда это упрощает тестирование и замену реализаций.
- Используй `dataclass` или существующие модели проекта по назначению.
- Не злоупотребляй наследованием.
- Не создавай абстрактные классы без реальной необходимости.
- Используй современные возможности Python в пределах версии проекта.
- Не маскируй ошибки типизации через `type: ignore` без объяснения.

Все внешние данные должны проходить проверку.

Type hints не заменяют runtime-валидацию.

## 7. Асинхронность

Используй `async` только там, где это действительно необходимо.

Правила:

- Не блокируй event loop синхронными длительными операциями.
- Не вызывай синхронный I/O непосредственно из async-контекста, если это блокирует event loop.
- Не смешивай sync и async API без необходимости.
- Используй `asyncio.gather` только для независимых операций.
- Корректно обрабатывай cancellation.
- Не проглатывай `CancelledError`.
- Учитывай таймауты и ограничения параллелизма.

Не превращай обычную синхронную функцию в async только ради единообразия.

## 8. Работа с данными

- Разделяй модели БД и DTO/API schemas.
- Не возвращай ORM-модели напрямую во внешний API без явного решения.
- Не выполняй запросы к БД в циклах без необходимости.
- Учитывай транзакции.
- Определяй границы транзакций.
- Не допускай скрытых изменений данных в функциях чтения.
- Используй миграции для изменения схемы.
- Не изменяй существующие данные без явного разрешения.

Не создавай второй механизм работы с БД, если он уже существует.

## 9. Конфигурация и секреты

- Храни конфигурацию централизованно.
- Не зашивай адреса сервисов, пароли и ключи в код.
- Используй переменные окружения и существующий config layer.
- Разделяй настройки разработки, тестирования и production.
- Проверяй обязательные параметры при старте.
- Не выводи секреты в логах.
- Не читай и не публикуй содержимое `.env`.

## 10. Исключения и логирование

- Используй специфичные исключения.
- Не перехватывай `Exception` без конкретной причины.
- Не используй `except:`.
- Не возвращай фиктивный успешный результат после ошибки.
- Не используй исключения для обычного управления потоком.
- Логируй контекст ошибки, но не секреты.
- Используй уровни логирования по назначению.
- Не дублируй один и тот же traceback на каждом уровне.

## 11. Зависимости

- Используй существующий package manager.
- Не устанавливай библиотеки без необходимости.
- Не меняй lock-файл вручную.
- Не обновляй все зависимости ради одной задачи.
- Проверяй совместимость версий.
- Не добавляй библиотеку, если задачу разумно решить существующими средствами.

## 12. TDD

Основной цикл:

RED → GREEN → REFACTOR.

1. Определи ожидаемое поведение.
2. Напиши тест.
3. Запусти его и убедись, что он падает по ожидаемой причине.
4. Реализуй минимальное решение.
5. Убедись, что тест проходит.
6. Проведи рефакторинг.
7. Повтори проверки.

Покрывай:

- Бизнес-логику.
- Валидацию.
- Граничные значения.
- Исключения.
- Работу с БД.
- Интеграции.
- Асинхронные сценарии.

Не подменяй интеграционные тесты полностью замоканными тестами.

## 13. Безопасность

Учитывай:

- SQL injection.
- Command injection.
- Path traversal.
- SSRF.
- Небезопасную десериализацию.
- Утечки секретов.
- Ошибки авторизации.
- Небезопасную обработку файлов.
- Некорректную проверку пользовательского ввода.

Не используй `eval` и `exec` для обработки недоверенных данных.

Не считай проверку на уровне API достаточной, если бизнес-операция может быть вызвана другими путями.

## 14. Работа AI-модели

- Сначала исследуй затрагиваемый код.
- Найди существующие аналоги.
- Определи минимальные изменения.
- Составь короткий план.
- Не переписывай несвязанные модули.
- Не создавай новые абстракции без причины.
- Не меняй публичные интерфейсы без проверки потребителей.
- При архитектурной неопределённости остановись и спроси.

Режимы:

- Исследование — только чтение.
- Разработка — реализация согласованной задачи.
- Исправление — воспроизведение, тест, исправление.
- Рефакторинг — изменение структуры без изменения поведения.
- Code Review — только замечания, без исправлений.

## 15. Проверки перед завершением

Выполни подходящие проверки:

- Formatter.
- Linter.
- Type checker.
- Unit tests.
- Integration tests.
- Сборка или запуск приложения.
- Проверка логов.
- Проверка Git diff.

Не заявляй о выполненной проверке, если команда не запускалась.

## 16. Итоговый отчёт

Укажи:

1. Что сделано.
2. Какие файлы изменены.
3. Какие тесты написаны.
4. Какие проверки выполнены.
5. Результаты проверок.
6. Нерешённые проблемы.
7. Риски и неподтверждённые предположения.

## 17. Главный принцип

Пиши минимальный, типизированный, тестируемый код, который соответствует архитектуре проекта и не создаёт лишней сложности.
