# React Engineering Skill

## 1. Назначение

Этот Skill определяет обязательные инженерные правила для AI-моделей, работающих с проектами на React и TypeScript.

Цели:

- Поддерживать существующую архитектуру проекта.
- Предотвращать хаотичное создание файлов и компонентов.
- Обеспечивать предсказуемую структуру кода.
- Исключать дублирование логики и функциональности.
- Обеспечивать корректную работу с API, состоянием и хранилищами.
- Применять TDD и автоматизированное тестирование.
- Поддерживать производительность, безопасность и расширяемость.
- Не допускать необоснованных архитектурных изменений.

Правила применяются ко всем задачам: разработке, исправлению ошибок, рефакторингу, интеграции API и code review.

## 2. Приоритет правил

При работе учитывай следующие уровни:

1. Прямые требования пользователя.
2. Инструкции проекта (`AGENTS.md`, `CLAUDE.md` и аналогичные).
3. Существующая архитектура и соглашения проекта.
4. Настоящий Skill.
5. Общие рекомендации React и TypeScript.

Если правила противоречат друг другу, не выбирай решение молча. Определи конфликт и сообщи о нём.

**Запрещено:**
- Переписывать существующую архитектуру ради соответствия этому Skill.
- Создавать второй механизм для уже существующей функциональности.
- Устанавливать новые библиотеки без необходимости и согласования.
- Менять публичные контракты без проверки всех потребителей.
- Делать массовые изменения, не связанные с задачей.

## 3. Обследование проекта перед работой

До изменения кода обязательно:

1. Прочитать применимые инструкции проекта.
2. Изучить `package.json` и используемый package manager.
3. Определить версии React и TypeScript.
4. Изучить структуру затрагиваемого участка.
5. Найти существующие аналоги нужной функциональности.
6. Определить используемые библиотеки:
   - Router;
   - State Management;
   - Data Fetching;
   - Form Management;
   - Validation;
   - Testing;
   - Styling.
7. Найти существующие API-клиенты, storage-адаптеры и общие компоненты.
8. Определить команды проверки проекта.

Не делай выводы по названиям файлов. Открывай исходный код и проверяй реальные связи.

Не исследуй весь проект, если задача затрагивает один изолированный модуль. Изучай только необходимую область и её зависимости.

Перед изменениями проверь `git status`. Не перезаписывай чужие незакоммиченные изменения.

## 4. Архитектура приложения

### 4.1. Общие принципы

- Разделяй ответственность между UI, бизнес-логикой, данными и инфраструктурой.
- Компоненты должны решать ограниченную задачу.
- Не смешивай отображение, сетевые запросы и сложную бизнес-логику в одном компоненте.
- Выноси повторно используемую логику в hooks или сервисы по назначению.
- Не создавай абстракции без реальной необходимости.
- Не допускай циклических зависимостей.
- Избегай чрезмерной вложенности каталогов.
- Не создавай универсальные компоненты с десятками несвязанных параметров.

### 4.2. Рекомендуемая структура

Если проект уже имеет архитектуру, следуй ей. Если архитектура отсутствует, для нового проекта используй feature-oriented подход.

Пример:

```text
src/
├── app/
│   ├── App.tsx
│   ├── providers/
│   ├── router/
│   └── config/
│
├── pages/
│   ├── DashboardPage/
│   │   ├── DashboardPage.tsx
│   │   └── index.ts
│   └── LoginPage/
│       ├── LoginPage.tsx
│       └── index.ts
│
├── features/
│   ├── auth/
│   │   ├── api/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── model/
│   │   ├── schemas/
│   │   ├── types/
│   │   ├── utils/
│   │   └── index.ts
│   │
│   └── projects/
│       ├── api/
│       ├── components/
│       ├── hooks/
│       ├── model/
│       ├── types/
│       └── index.ts
│
├── entities/
│   ├── user/
│   └── project/
│
├── shared/
│   ├── api/
│   ├── components/
│   ├── hooks/
│   ├── lib/
│   ├── storage/
│   ├── styles/
│   ├── types/
│   └── utils/
│
├── assets/
└── main.tsx
```

Это ориентир, а не обязательное требование переносить все файлы в перечисленные каталоги.

### 4.3. Что куда помещать

**app/**

Инициализация приложения, глобальные providers, конфигурация, маршрутизация и сборка приложения.

**pages/**

Страницы, соответствующие маршрутам. Страница объединяет необходимые features и entities, но не должна содержать всю бизнес-логику приложения.

**features/**

Самостоятельные пользовательские сценарии и функциональные возможности: auth, search, notifications, project-editor, payments.

**entities/**

Бизнес-сущности и их базовые представления: user, project, order, organization.

**shared/**

Независимый от конкретной бизнес-функции переиспользуемый код: UI, общие hooks, API-инфраструктура, storage, утилиты и типы.

**assets/**

Изображения, шрифты, иконки и другие статические ресурсы.

### 4.4. Правила зависимостей

Предпочтительное направление:

`app → pages → features → entities → shared`

Правила:

- Нижележащие уровни не должны импортировать верхние.
- `shared` не должен зависеть от бизнес-сущностей.
- `entities` не должны зависеть от конкретных пользовательских сценариев.
- Feature не должна импортировать внутренние файлы другой feature в обход её публичного интерфейса.
- Не создавай циклические импорты.

Если проект использует другую архитектуру, соблюдай её существующие границы.

## 5. Правила именования

Используй единый стиль во всём проекте.

| Объект | Стиль | Пример |
|---|---|---|
| React-компоненты | PascalCase | `UserProfile.tsx` |
| Страницы | PascalCase + Page | `LoginPage.tsx` |
| Hooks | camelCase, use-префикс | `useAuth.ts` |
| Утилиты | camelCase | `formatDate.ts` |
| API-модули | camelCase | `userApi.ts` |
| Типы | PascalCase | `User.ts` |
| Константы | UPPER_SNAKE_CASE | `API_BASE_URL` |
| Тесты | имя + test/spec | `UserProfile.test.tsx` |
| CSS Modules | имя компонента | `UserProfile.module.css` |
| Каталоги компонентов | PascalCase или стиль проекта | `UserProfile/` |
| Feature-каталоги | kebab-case | `user-profile/` |

Дополнительные правила:

- Один основной React-компонент — один файл.
- Имя файла компонента совпадает с именем экспортируемого компонента.
- Не используй названия `common.ts`, `helpers.ts`, `misc.ts` для несвязанных функций.
- Не используй `index.ts` как место хранения всей логики модуля. Он предназначен для публичного экспорта.
- Не создавай несколько файлов с одинаковой ответственностью.
- Не добавляй суффиксы `New`, `Old`, `Final`, `V2` без архитектурной причины.
- Не называй компоненты слишком общо: `Component`, `Widget`, `Manager`, `Handler`.

## 6. React-компоненты

### 6.1. Ответственность

Компонент должен отвечать за ограниченную часть интерфейса.

Разделяй:

- Представление.
- Управление состоянием.
- Бизнес-логику.
- Получение и преобразование данных.
- Побочные эффекты.

Не выноси каждую строку кода в отдельный компонент или hook. Декомпозиция должна улучшать читаемость и повторное использование.

### 6.2. Props

- Все props должны быть типизированы.
- Не используй `any`.
- Не передавай компоненту данные, которые он не использует.
- Не создавай огромные наборы необязательных props для разных несвязанных сценариев.
- Используй discriminated unions для взаимоисключающих вариантов поведения.
- Не мутируй props.

Переиспользуй существующий компонент заголовка страницы и его поддерживаемые свойства вместо создания дубликатов; сначала проверь дизайн-систему и соглашения целевого проекта.

### 6.3. Hooks

- Соблюдай Rules of Hooks.
- Вызывай hooks только на верхнем уровне компонентов и других hooks.
- Не вызывай hooks внутри условий, циклов и вложенных функций.
- Собственные hooks называй с `use`.
- Не создавай hook, если он только переименовывает одну очевидную операцию.
- Избегай скрытых побочных эффектов.

### 6.4. Effects

`useEffect` предназначен для синхронизации с внешними системами, а не для организации всей бизнес-логики.

Не используй effect для:

- Вычисления значений, которые можно получить из props или state.
- Дублирования состояния.
- Реакции на пользовательские события, которые лучше обрабатывать непосредственно в обработчике.
- Последовательного запуска цепочки эффектов вместо явного сценария.

Обязательно:

- Указывай корректные зависимости.
- Учитывай cleanup.
- Предотвращай устаревшие асинхронные операции.
- Учитывай повторный запуск эффектов в Strict Mode.
- Не подавляй предупреждения ESLint без обоснования.

### 6.5. State

- Держи состояние максимально близко к месту использования.
- Не поднимай состояние выше необходимого.
- Не храни в state то, что можно вычислить.
- Не дублируй одни и те же данные в нескольких хранилищах.
- Используй immutable updates.
- Разделяй локальное UI-состояние и состояние серверных данных.

Не добавляй глобальный state manager, если задача решается локальным состоянием или уже имеющимся инструментом проекта.

## 7. TypeScript

- Используй строгую типизацию.
- Не используй `any` для обхода ошибок компиляции.
- Не применяй `as` без необходимости и проверки корректности.
- Предпочитай `unknown` для действительно неизвестных данных.
- Проверяй внешние данные во время выполнения.
- Не путай TypeScript-типы с runtime-валидацией.
- Используй `type` и `interface` последовательно.
- Не дублируй определения одного контракта в разных модулях.
- Не используй необоснованные non-null assertions (`!`).

Для API и пользовательского ввода используй runtime-схемы, если в проекте уже есть соответствующая библиотека.

Пример:

```ts
export interface User {
  id: string;
  email: string;
  name: string;
}

export type AuthStatus =
  | 'authenticated'
  | 'anonymous'
  | 'loading';
```

Не используй тип `User` как тип ответа любого API только потому, что в ответе есть поле `id`.

## 8. Работа с API

### 8.1. Общие правила

- Все HTTP-запросы должны проходить через согласованный API-слой.
- Не вызывай `fetch` или `axios` непосредственно из произвольных UI-компонентов.
- Не дублируй базовый URL, заголовки и обработку ошибок.
- Не смешивай сетевую логику с отображением.
- Используй существующий HTTP-клиент.
- Не создавай второй API-клиент без необходимости.

Рекомендуемое разделение:

```text
shared/
└── api/
    ├── client.ts
    ├── errors.ts
    ├── types.ts
    └── interceptors.ts

features/
└── auth/
    └── api/
        ├── authApi.ts
        └── authTypes.ts
```

`shared/api` содержит инфраструктуру запросов.

`features/<feature>/api` содержит методы конкретной бизнес-функции.

### 8.2. Контракты API

Для каждого запроса определяй:

- HTTP method.
- Endpoint.
- Request type.
- Response type.
- Возможные ошибки.
- Правила авторизации.
- Правила обработки отмены запроса.

Пример:

```ts
export interface LoginRequest {
  email: string;
  password: string;
}

export interface LoginResponse {
  user: User;
}
```

Не придумывай API-контракты, если Backend уже существует. Сначала изучи реальные endpoints и схемы.

Если Backend ещё не реализован, отделяй согласованный контракт от временной mock-реализации.

### 8.3. Обработка ошибок

Единообразно обрабатывай:

- Сетевые ошибки.
- HTTP 400 — ошибки запроса.
- HTTP 401 — отсутствие или недействительность авторизации.
- HTTP 403 — недостаточно прав.
- HTTP 404 — ресурс не найден.
- HTTP 409 — конфликт.
- HTTP 422 — ошибки валидации.
- HTTP 429 — ограничение частоты запросов.
- HTTP 5xx — серверные ошибки.

Не считай HTTP 200 гарантией корректных данных.

Не показывай пользователю технические stack traces, внутренние адреса серверов и секретные сведения.

Не скрывай ошибки пустым `catch`.

### 8.4. Асинхронные запросы

- Учитывай loading, success, error и empty states.
- Используй отмену запросов, если результат больше не нужен.
- Предотвращай применение устаревших результатов.
- Не допускай гонок запросов.
- Не запускай повторные запросы без необходимости.
- Не делай бесконечные retry при ошибках.
- Учитывай идемпотентность операций.

### 8.5. Серверное состояние

Если проект использует TanStack Query, SWR или другой инструмент серверного состояния, используй его последовательно.

Не смешивай серверные данные с локальным UI-state без необходимости.

Определи:

- Query keys.
- Правила кеширования.
- Время актуальности данных.
- Инвалидацию.
- Обновление кеша после мутаций.
- Правила повторных запросов.

Не создавай параллельный кеш поверх уже используемого механизма.

## 9. Работа с хранилищами (Storage)

### 9.1. Сначала определить тип данных

Перед выбором хранилища ответь на вопросы:

1. Кто является источником истины?
2. Должны ли данные переживать перезагрузку страницы?
3. Должны ли данные синхронизироваться между вкладками?
4. Нужен ли доступ к ним после закрытия браузера?
5. Содержат ли данные чувствительную информацию?
6. Должны ли данные быть доступны другим пользователям или устройствам?

Не выбирай localStorage только потому, что это простой способ сохранить значение.

### 9.2. Назначение хранилищ

**React state**

Для временного состояния интерфейса:

- Открыта ли модалка.
- Выбранная вкладка.
- Состояние раскрытия меню.
- Значения временных элементов управления.

**Context**

Для ограниченного набора общих данных и зависимостей, доступных части дерева компонентов.

Не превращай Context в универсальную замену state manager.

**State manager**

Для разделяемого клиентского состояния, когда этого требует сложность приложения.

Используй существующую библиотеку проекта.

**TanStack Query / SWR**

Для серверного состояния, кеширования и синхронизации с API.

**localStorage**

Для небольших несекретных данных, которые должны сохраняться между сессиями браузера:

- Настройки интерфейса.
- Тема.
- Предпочтения пользователя.
- Несекретные пользовательские настройки.

Не используй localStorage для хранения паролей, refresh tokens, session IDs и другой чувствительной информации.

**sessionStorage**

Для временных данных в пределах вкладки браузера. Не считай его защищённым хранилищем секретов.

**IndexedDB**

Для больших структурированных данных, офлайн-данных и локальных файлов, когда требуется долговременное клиентское хранение.

**Cookies**

Для передачи данных между браузером и сервером. При использовании cookie-based sessions применяй серверные настройки `HttpOnly`, `Secure`, подходящий `SameSite`, а также защиту от CSRF с учётом архитектуры приложения.

### 9.3. Запреты

- Не храни секреты в localStorage.
- Не дублируй один набор данных в localStorage, Context и глобальном state без необходимости.
- Не обращайся к storage напрямую из десятков компонентов.
- Не используй storage как замену Backend.
- Не считай данные браузерного хранилища доверенными.
- Не сохраняй данные без определённой политики очистки.
- Не создавай собственный механизм шифрования вместо использования корректных механизмов безопасности платформы.

### 9.4. Storage abstraction

Для повторно используемой логики создавай централизованный адаптер.

Пример:

```text
shared/
└── storage/
    ├── storage.types.ts
    ├── localStorage.adapter.ts
    ├── sessionStorage.adapter.ts
    └── index.ts
```

Необязательно создавать все перечисленные файлы: добавляй только реально нужные реализации.

Пример интерфейса:

```ts
export interface StorageAdapter {
  get<T>(key: string): T | null;
  set<T>(key: string, value: T): void;
  remove(key: string): void;
  clear(): void;
}
```

Учитывай:

- JSON serialization/deserialization.
- Ошибки доступа к storage.
- Некорректные или устаревшие данные.
- Версионирование формата.
- Ограничения браузера.
- SSR и отсутствие `window`.
- Политику очистки данных.

Не используй `clear()` для очистки одного функционального раздела, если он удалит чужие данные. Предпочитай изолированные ключи и точечное удаление.

### 9.5. Авторизация и storage

Предпочтительный подход для браузерных приложений — серверная сессия с защищённой cookie, если Backend и архитектура это поддерживают.

Не сохраняй access token или refresh token в localStorage по умолчанию.

Не реализуй собственную схему авторизации без согласования с Backend.

## 10. Формы и валидация

- Используй существующую библиотеку форм.
- Не создавай собственную систему валидации, если в проекте уже есть подходящая.
- Разделяй валидацию интерфейса и серверную валидацию.
- Не считай клиентскую валидацию защитой Backend.
- Типизируй значения и ошибки форм.
- Отображай понятные сообщения.
- Не теряй пользовательские данные при временных ошибках.
- Учитывай отправку формы по Enter.
- Блокируй повторную отправку, если операция ещё выполняется.

Для каждой формы предусмотрены состояния: initial, validating, submitting, success и error — в объёме, необходимом конкретному сценарию.

## 11. Стили и дизайн-система

Перед созданием или изменением UI изучи существующие:

- Design tokens.
- Цветовую палитру.
- Типографику.
- UI-компоненты.
- Систему отступов.
- Breakpoints.
- Подход к CSS.

Правила:

- Используй существующие токены.
- Не дублируй стили компонентов.
- Не создавай новую палитру.
- Не используй глобальные CSS-селекторы для локальных задач.
- Не переопределяй стили чужих компонентов без необходимости.
- Не используй `!important` для маскировки проблем каскада.
- Учитывай hover, focus, active, disabled, loading, error.
- Поддерживай клавиатурную навигацию.
- Обеспечивай видимый focus state.
- Проверяй мобильные и десктопные размеры.

CSS Modules, styled-components, Tailwind и другие подходы используй в соответствии с существующей системой проекта. Не смешивай несколько подходов без необходимости.

## 12. Маршрутизация

- Используй существующую библиотеку маршрутизации.
- Не создавай собственный Router.
- Не дублируй конфигурацию маршрутов.
- Разделяй маршруты, страницы и layouts.
- Учитывай прямой переход по URL.
- Учитывай перезагрузку страницы.
- Обрабатывай неизвестные маршруты.
- Учитывай состояния авторизации и прав доступа.
- Не полагайся только на Frontend-защиту: Backend обязан проверять доступ самостоятельно.

Для больших приложений используй lazy loading страниц, если это соответствует архитектуре проекта.

## 13. TDD — Test Driven Development

TDD является предпочтительным рабочим процессом для разработки и исправления функциональности.

Основной цикл:

**RED → GREEN → REFACTOR**

### 13.1. RED

1. Определи ожидаемое поведение.
2. Определи граничные случаи.
3. Напиши тест, описывающий требуемое поведение.
4. Запусти тест.
5. Убедись, что он падает по ожидаемой причине.

Тест, который падает из-за неправильной настройки окружения, не подтверждает корректность RED.

### 13.2. GREEN

1. Напиши минимальный код, необходимый для прохождения теста.
2. Не реализуй дополнительные сценарии, которых нет в требованиях.
3. Запусти новый тест.
4. Запусти связанные существующие тесты.
5. Убедись, что они проходят.

### 13.3. REFACTOR

1. Устрани дублирование.
2. Улучши имена и структуру.
3. Проверь границы ответственности.
4. Не меняй внешнее поведение.
5. Повтори тесты после рефакторинга.

### 13.4. Требования к тестам

Пиши тесты для:

- Бизнес-логики.
- Компонентов с существенным поведением.
- Hooks со сложной логикой.
- API-адаптеров.
- Storage-адаптеров.
- Форм и валидации.
- Ошибок и граничных состояний.
- Регрессий.

Не пиши тесты ради количества.

Тест должен проверять наблюдаемое поведение, а не внутреннюю реализацию.

Не привязывай тест к деталям реализации, которые можно изменить без изменения поведения.

### 13.5. Исключения

Для простых визуальных изменений, текстовых правок и задач без логики допустимо использовать проверки без отдельного TDD-цикла.

Если существующая тестовая инфраструктура отсутствует, не устанавливай её самовольно. Сообщи об этом и предложи минимальный путь внедрения.

## 14. Тестирование

Используй существующий стек проекта.

Рекомендуемые инструменты, если проект ещё не выбрал аналоги:

- Vitest — unit и component tests.
- React Testing Library — тестирование компонентов.
- Playwright — E2E и браузерные сценарии.
- MSW — mock HTTP API в тестах.

Проверяй:

1. Успешные сценарии.
2. Ошибки.
3. Пустые состояния.
4. Граничные значения.
5. Повторные действия.
6. Асинхронные сценарии.
7. Корректность отображения.
8. Регрессии соседней функциональности.

Не заменяй реальные интеграционные проверки тестами, которые полностью имитируют проверяемую систему.

## 15. Производительность

- Не оптимизируй код без причины.
- Не используй `useMemo` и `useCallback` автоматически.
- Не создавай ненужные глобальные состояния.
- Не допускай больших компонентов с избыточными зависимостями.
- Используй lazy loading для тяжёлых страниц и модулей, если это оправдано.
- Контролируй повторные запросы.
- Не загружай большие данные целиком, если доступна пагинация.
- Учитывай виртуализацию больших списков.
- Не загружай тяжёлые ресурсы без необходимости.
- Проверяй влияние изменений на размер бандла, если они затрагивают зависимости или крупные модули.

## 16. Безопасность

Обязательно учитывай:

- XSS.
- Небезопасный `dangerouslySetInnerHTML`.
- Валидацию внешних данных.
- Безопасную обработку пользовательского ввода.
- Безопасное хранение токенов и сессий.
- Утечки секретов в логах.
- Небезопасные URL и перенаправления.
- Уязвимые зависимости.
- Проверку прав на стороне Backend.

Не считай скрытие кнопки или маршрута достаточной проверкой доступа.

Не добавляй секреты, ключи и пароли в исходный код.

Не отключай существующие механизмы безопасности ради удобства разработки.

## 17. Доступность (Accessibility)

- Используй семантические HTML-элементы.
- Предусматривай доступные имена элементов управления.
- Связывай поля форм с label.
- Поддерживай клавиатурную навигацию.
- Обеспечивай видимый focus.
- Используй ARIA только там, где семантического HTML недостаточно.
- Не используй цвет как единственный способ передачи информации.
- Учитывай контрастность.
- Проверяй диалоги, меню и интерактивные элементы.

## 18. Работа AI-модели

### 18.1. Перед реализацией

Сначала:

1. Пойми задачу.
2. Изучи затрагиваемую часть проекта.
3. Найди существующие реализации.
4. Определи минимальный набор изменений.
5. Определи тесты.
6. Составь короткий план.

Если задача неоднозначна и от решения зависит архитектура, задай вопрос до реализации.

### 18.2. Во время реализации

- Работай небольшими логическими этапами.
- Не меняй несвязанные модули.
- Не переписывай рабочий код без причины.
- Не создавай временные файлы без необходимости.
- Не добавляй зависимости без согласования.
- Не подавляй ошибки типизации и линтера.
- Не оставляй фиктивные реализации вместо требуемой функциональности.
- Не маскируй ошибки пустыми обработчиками.
- Не меняй публичные API без проверки потребителей.

### 18.3. Работа с неопределённостью

Остановись и сообщи пользователю, если:

- Не найден ожидаемый механизм проекта.
- Обнаружены противоречащие друг другу архитектурные решения.
- Требуется изменение контракта API.
- Требуется миграция данных.
- Требуется изменение схемы авторизации.
- Неясно, где должен находиться новый модуль.
- Невозможно проверить безопасность решения.
- Требуется существенно расширить объём задачи.

Не додумывай архитектуру и не подменяй требования собственными предположениями.

### 18.4. Режимы работы

**Исследование**

Только чтение и анализ. Изменения запрещены.

**Разработка**

Реализация согласованной функциональности с тестами.

**Исправление ошибки**

Воспроизвести ошибку, найти причину, написать регрессионный тест, исправить минимально необходимым образом.

**Рефакторинг**

Изменить структуру без изменения внешнего поведения. До и после — одинаковые проверки.

**Code Review**

Ничего не исправлять. Выдавать замечания с указанием файла, строки, причины, последствий и способа исправления.

Не переключайся между режимами самостоятельно, если это меняет согласованный объём работ.

## 19. Проверка перед завершением

Перед отчётом:

1. Проверь `git diff`.
2. Убедись, что нет случайных изменений.
3. Запусти TypeScript typecheck.
4. Запусти ESLint.
5. Запусти затронутые тесты.
6. Запусти сборку.
7. Проверь браузерное поведение, если задача затрагивает UI.
8. Проверь консоль браузера.
9. Проверь сетевые ошибки.
10. Убедись, что существующая функциональность не сломана.

Не утверждай, что проверка выполнена, если команда не запускалась.

Если проверка не может быть выполнена, укажи причину.

Не исправляй посторонние ошибки, обнаруженные во время проверок, без согласования.

## 20. Критерии качества

Изменение считается качественным, если:

- Решает именно поставленную задачу.
- Соответствует архитектуре проекта.
- Не дублирует существующую функциональность.
- Имеет корректные типы.
- Не создаёт необоснованных зависимостей.
- Покрыто необходимыми тестами.
- Не нарушает существующие контракты.
- Не ухудшает безопасность.
- Не создаёт очевидных проблем производительности.
- Проверено подходящими инструментами.

## 21. Итоговый отчёт

После выполнения задачи предоставь краткий отчёт:

### Реализовано
Что конкретно сделано.

### Изменённые файлы
Список файлов и назначение изменений.

### Тесты и проверки
Какие команды выполнены и их фактические результаты.

### Результат
Что работает и как проверено.

### Остаточные проблемы
Что не удалось сделать, какие ограничения обнаружены.

### Риски и предположения
Только если они действительно существуют.

Не заявляй о полном успехе, если обязательные проверки не пройдены.

## 22. Главные принципы

1. Understand before changing.
2. Test before implementation.
3. Minimal change.
4. No duplicated architecture.
5. Explicit contracts.
6. Correct separation of concerns.
7. Secure by default.
8. Evidence-based completion.
9. Stop on uncertainty.
10. Preserve working functionality.

**Лучший результат — не максимальное количество написанного кода, а минимальное корректное изменение, которое решает задачу и не создаёт новых проблем.**
